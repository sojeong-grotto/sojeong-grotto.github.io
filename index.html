조이스틱으로 조종하는 무선 RC카에서, 차체가 기울면 LCD 속 캐릭터가 따라 움직이도록 기울기 센서와 화면을 연결했습니다.

결과

기울기를 왼쪽·가운데·오른쪽 3단계로 안정적으로 표시하고, 바뀐 부분만 다시 그려 화면 깜빡임을 없앴습니다. LCD가 예상과 다르게 응답하던 문제는 빠진 배선을 찾아 해결했습니다.

STM32F411RE 보드 두 대를 블루투스 UART로 연결해 조이스틱으로 조종하는 RC카입니다. 저는 차체의 기울기를 읽어 LCD 캐릭터의 위치와 표정을 바꾸는 센서-화면 연동을 맡았습니다.

데이터 흐름 · 담당 영역
표시 안정화 1

미세 진동에 화면이 떨리지 않게

중앙 부근에 데드존을 두고, 기울기가 커질수록 빠르게 움직이는 3제곱 이징 곡선으로 바꿔 작은 흔들림은 무시하고 의도한 기울기만 반영했습니다.

표시 안정화 2

바뀐 부분만 다시 그리기

매 주기 화면 전체를 다시 그리면 깜빡이고 SPI 전송량이 늘었습니다. 이전 위치와 겹치지 않는 영역만 지우고 새 위치를 그리는 부분 갱신으로 바꿨습니다.

트러블슈팅

LCD ID 값이 예상과 다르게 읽힘

증상
RDDID(0x04) 명령으로 컨트롤러 ID를 읽으면 기대값(0x93, 0x41)과 달랐습니다.
원인
MISO 배선이 연결되지 않아 플로팅 상태의 핀 값이 우연히 읽혔습니다.
해결
FillScreen 색 채우기로 초기화 성공을 별도로 눈으로 확인하고 배선을 점검했습니다.
배운 점
레지스터 읽기는 배선 상태에 좌우되므로 화면 출력 검증을 함께 둡니다.
팀 결과조이스틱 입력 → 패킷 송수신 → 좌우 모터 PI 제어를 10ms 주기로 안정적으로 운용했고, 초음파 10cm 장애물 정지와 500ms fail-safe를 함께 동작시켰습니다. 계획했던 카메라(OV7670) 영상 저장은 기간 안에 완성하지 못해 최종 시스템에서 제외했습니다.

결과

지정 적재·선택 비움을 수동으로 실행할 수 있게 했고, 설비가 동작을 마치는 순간 화면의 램프·메시지도 같은 상태를 보여 주도록 맞췄습니다.

금속·비금속 소재를 드릴로 가공하고, 가공 시간과 횟수에 따라 창고 6칸 중 적재 위치를 정하는 설비입니다. 저는 수동 시퀀스와 HMI 화면 구성·PLC 연동을, 팀원은 자동 시퀀스를 맡았습니다.

적재 위치 결정 규칙

가공 시간으로 열을, 가공 횟수로 층을 정합니다. 칸별 소재 수는 D101–D106에 저장합니다.

담당 기능
  • 지정 적재(수동) · 가공 시간·횟수를 입력하면 드릴 동작 후 위치를 정해 적재하고, 끝나면 시퀀스를 초기화합니다.
  • 선택 비움(수동) · 적재된 칸을 골라 해당 위치의 소재만 비웁니다.
  • 사전 조건 확인 · 적재 전에는 칸이 비었는지, 비움 전에는 소재가 있는지 확인하고 아니면 하단 메시지로 알립니다.
  • HMI 4개 화면 · 메인, 서보, 자동, 수동 화면을 만들고 버튼·램프·메시지를 PLC 디바이스에 연결했습니다.
사전 조건 확인 흐름 (지정 적재)
메시지 화면

조건이 맞지 않으면 동작하지 않고 이유를 화면 하단에 알립니다.

PLC 동작과 HMI 램프·메시지의 표시 시점이 어긋남

PROBLEM
설비는 적재를 끝냈는데 HMI 램프가 늦게 켜지거나 이전 메시지가 남았습니다.
CAUSE
PLC 내부 비트와 HMI 표시용 디바이스가 분리되어, 상태가 바뀌는 시점과 화면 값이 갱신되는 시점이 달랐습니다.
SOLUTION

그룹사 통합 메신저 Qpost

큐텐과 3개 계열사, 약 1,500명이 쓰는 통합 메신저로 재구축하고 외부 시스템과 연결

회사큐텐테크놀로지
기간2017.08 – 2024.08
직급선임연구원
규모4개사 · 약 1,500명
한 줄 요약

업무 목적과 사용자에 따라 나뉘어 있던 메신저를, 큐텐과 3개 계열사 직원 약 1,500명이 함께 쓰는 하나의 통합 메신저로 다시 만들었습니다.

결과

기존 사용자 데이터를 새 구조로 옮기는 마이그레이션과 Microsoft Teams 메시지 연동을 구현했고, 사용자 PC에서만 발생하던 비정상 종료의 원인을 찾아 해결했습니다.

그룹사가 늘면서 업무 목적과 사용자에 따라 따로 운영되던 메신저를 하나로 재구축했습니다. 기능을 단순히 합치지 않고, 사용자 데이터가 어디서 생겨 어떤 경로로 화면에 닿는지부터 분석했습니다.

기존 구조 → 통합 구조
담당 범위
  • 구조 설계 · 기존 메신저의 구조와 데이터 흐름을 분석해 통합 구조 설계
  • DB 설계 · 계열사별 조직도를 기준으로 사용자를 관리하는 테이블 구성
  • 마이그레이션 · 기존 사용자의 로컬 DB를 통합 구조로 옮기는 전환 로직
  • 이벤트 처리 · 메신저 내부 이벤트를 Broker 라이브러리로 처리
  • 핵심 화면 · 로그인, 조직도, 채팅 목록, 모바일 포워딩, 설정
그 밖의 7년간 개발
  • 그룹사 친구 추가·삭제, 스티커, 오픈 채팅
  • 신규 그룹사 전용 메신저와 조직도, 출퇴근 체크인·체크아웃
  • 모바일 수신 전용 채팅창, 메신저 전체 디자인 리뉴얼
  • SecurityManager · PC의 Hotfix 내역과 설치 프로그램을 서버와 동기화하고 패치·삭제 알림을 받는 구조 설계
  • Teams 조직도 앱(C# Blazor) 기능 추가
Microsoft Teams 채팅 연동

API를 일정 주기로 조회하되 마지막 업데이트 시각을 로컬 DB에 저장해 비교하는 방식으로 새 메시지만 골라, 같은 메시지가 두 번 뜨거나 빠지는 경우를 줄였습니다. 전용 채팅 UI는 사용자 피드백을 받아 여러 차례 개선했습니다.

사용자 환경에서만 발생한 비정상 종료

증상
특정 사용자 PC에서만 메신저가 종료되고, 개발 환경에서는 재현되지 않았습니다.
추적
발생 당시 사용 조건을 확인하고, WinDbg로 크래시 덤프의 호출 스택을 따라 실행 흐름을 거슬러 올라갔습니다.
원인
모바일 앱으로 대화하던 상대가 PC 메신저로 넘어와 대화를 이어갈 때, 수신 패킷의 특정 속성이 비어 있어 메모리 참조 오류가 났습니다.
결과
빈 값을 처리하도록 수정해 종료를 막았고, 이후 새 기능마다 빈 값 같은 예외 조건을 먼저 점검합니다.
이전 회사 · 소프트보울 (2014–2016) · TrustForm

MFC로 만든 XML/XForms 웹 UI 도구를 유지보수하며 신한카드·국립중앙의료원 등 20여 개 고객사를 전담했습니다. 고객사마다 다른 요구에 맞춰 WinInet HTTPS 통신, XML→JSON 변환 API, HTTP 오류 시 에러 페이지 전환을 구현했고, 키보드 보안 모듈(nProtect NOS)을 화면 생성·포커스 진입·이탈 시점에 맞춰 연동했습니다.
